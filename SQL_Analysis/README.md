# Superstore Sales Analysis | PostgreSQL

SQL-проект по анализу продаж интернет-магазина на основе датасета Superstore. Проект показывает, как с помощью PostgreSQL пройти путь от загрузки и первичной проверки данных до бизнес-аналитики, сегментации клиентов, анализа скидок, временной динамики и использования оконных функций.

## О проекте

Цель проекта — не просто посчитать несколько KPI, а ответить на типичные вопросы Data Analyst:

- сколько выручки и прибыли генерирует бизнес;
- какие категории, подкатегории, регионы и клиенты дают основной вклад;
- как скидка связана с выручкой и прибыльностью;
- какие клиенты покупают чаще и приносят больше денег;
- как меняется выручка и прибыль во времени;
- где оконные функции помогают получить более глубокую аналитику.

Анализ построен последовательно: сначала подготовка и проверка данных, затем базовые KPI и разрезы бизнеса, после этого клиентская аналитика, временной анализ, оконные функции, ABC-анализ и когортный анализ.

Используется датасет **Superstore** с информацией о заказах, клиентах, товарах, категориях, регионах, скидках, продажах и прибыли.

## Что анализируется

### 1. Подготовка данных

Создаётся таблица `superstore`, после чего CSV загружается в PostgreSQL. В начале SQL-файла также отмечены основные вопросы качества данных и ограничения исходного скрипта.

### 2. Базовые бизнес-KPI

Рассчитываются выручка, прибыль, средняя продажа, средняя скидка, количество заказов и количество уникальных клиентов.

### 3. Анализ бизнеса по разрезам

Исследуются:

- способы доставки;
- клиентские сегменты;
- категории и подкатегории товаров;
- регионы;
- отдельные товары;
- крупнейшие и наименее прибыльные клиенты и продукты.

### 4. Оконные функции

В проекте показано несколько практических сценариев использования оконных функций:

- `RANK()` — ранжирование регионов и категорий;
- `ROW_NUMBER()` — ранжирование клиентов и товаров внутри групп;
- `NTILE(4)` — разделение клиентов на четыре группы по выручке;
- `LAG()` — сравнение текущего месяца или скидки с предыдущим значением;
- `SUM() OVER()` — накопительная выручка и доля категории в общей выручке.

### 5. Временной анализ

Рассчитываются месячная выручка и прибыль, рост выручки месяц к месяцу и накопительные показатели.

### 6. Анализ скидок

Исследуется зависимость между размером скидки, выручкой, прибылью и маржинальностью. Дополнительно значения скидок объединяются в диапазоны.

### 7. Анализ клиентов

Рассчитываются:

- Average Order Value (AOV);
- количество заказов на клиента;
- распределение клиентов по частоте покупок;
- доля повторных клиентов;
- квартильные группы клиентов по выручке.

### 8. ABC-анализ товаров

Товары распределяются на группы:

- **A** — первые 80% накопленной выручки;
- **B** — следующие 15%;
- **C** — оставшиеся 5%.

Это позволяет определить товары, которые формируют основную часть оборота.

### 9. Когортный анализ

Клиенты объединяются по году первой покупки. Для каждой когорты рассчитываются выручка, прибыль и количество заказов.

Важно: текущая версия показывает **когортную структуру и итоговую ценность когорт**, но не полноценный retention-анализ по месяцам после первой покупки.

## Ключевые аналитические приёмы

Один из важных моментов проекта — отделение уровня детализации данных от уровня бизнес-метрики.

Например, выручка рассчитывается как:

`SUM(sales)`

а средний чек — как:

`SUM(sales) / COUNT(DISTINCT order_id)`

Это важно, потому что одна строка таблицы не обязательно соответствует одному заказу. Один заказ может содержать несколько товарных строк.

Для маржинальности используется:

`SUM(profit) / SUM(sales) * 100`

Такой расчёт корректнее, чем среднее значение построчных маржинальностей, поскольку он учитывает общий объём продаж.

## Как запустить

1. Установить PostgreSQL.
2. Создать базу данных.
3. Открыть SQL-файл в pgAdmin, DBeaver или другом SQL-клиенте.
4. Выполнить создание таблицы.
5. Загрузить CSV в таблицу `superstore`.
6. Последовательно выполнить аналитические запросы.

В исходном скрипте команда `COPY` содержит локальный Windows-путь:

```sql
COPY superstore
FROM 'C:\Superstore.csv'
```

Перед запуском на другой машине этот путь необходимо изменить.

## Важные замечания по качеству данных

В исходной таблице поле региона называется `regoin`. Это, вероятно, опечатка. В текущем проекте название сохранено, чтобы SQL оставался совместимым с исходной структурой.

Поле `discount` в исходной версии объявлено как `INTEGER`. Если в CSV скидка хранится в формате `0.2`, `0.3` и т. п., для корректного хранения лучше использовать `NUMERIC`.

Также перед публикацией production-версии проекта стоит добавить отдельные проверки на `NULL`, дубликаты, некорректные даты и нулевую выручку при расчёте относительных показателей.

## Что можно улучшить дальше

Проект уже демонстрирует хороший набор SQL-инструментов для портфолио начинающего Data Analyst. Следующим уровнем можно добавить полноценный retention по когортам, более детальный анализ влияния скидки на маржинальность, RFM-сегментацию клиентов и визуализацию результатов в Power BI/Tableau.

## Результат

Проект демонстрирует не только знание синтаксиса SQL, но и подход к аналитической задаче: сформулировать бизнес-вопрос, выбрать подходящую гранулярность, агрегировать данные, применить оконные функции и интерпретировать полученный результат с точки зрения бизнеса.
